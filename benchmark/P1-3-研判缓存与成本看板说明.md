# P1-3 研判缓存与成本看板

## 配置与口径

- 仅缓存真实模型返回且结构校验成功的 MODEL 研判；规则降级和 Mock 模式不缓存。缓存键包含事件 ID、按日志 ID 与规则编码规范化的证据、模型地址与名称以及提示/校验版本；同一来源记录有效期 24 小时。模型或提示规则变更时需更新缓存版本。单实例内相同指纹并发请求合并；不同后端进程不共享锁，并发时仍可能重复调用模型。
- 缓存命中仍生成独立研判历史，保留来源研判 ID；本次耗时和新增输入/输出 token 为 0，不覆盖首次研判。
- 仅管理员可看成本统计。研判请求计数是新版本成功保存的请求，不包括旧历史、失败/限流请求；命中率=命中次数/已保存研判请求。
- 模型尝试包含重试、无效输出和失败；平均耗时按这些尝试的本机计时求均值；最近调用列表最多 100 条。模型连通性测试和旧版调用不计入。调用统计写入异常时保留研判结果并记录告警，故统计可能缺失。
- 节省 token 估算为每次命中来源研判已知的输入和输出 token 总数之和；缺失 usage 的来源估算为 0（下限），不等同账单。服务商未提供完整 usage 及失败调用的 token 为未知，尝试明细以未知展示、不纳入已知总量。历史研判自身展示的 token 字段仍沿用旧系统缺失用量按 0 存储的限制；请以尝试明细的未知提示为准。
- 新增表由 `schema.sql` 的 `CREATE TABLE IF NOT EXISTS` 在后端启动时创建；需要已有数据库用户具备建表权限，不清除既有数据。启动失败时先检查数据库权限和后端日志。

## 手动验收

1. 先确保使用最新代码构建并启动前后端。容器方式在仓库根目录执行 `docker compose up -d --build backend frontend`；此操作会重建应用容器但不删除数据库卷，重建前请先保存当前工作。
2. 管理员登录后进入“安全概览”，应出现“事件研判调用与缓存”区域；分析员账号不应看到该区域、调用统计接口应返回 403。
3. 默认 `LLM_MOCK=true` 只产生 `RULE_FALLBACK`，不能验证缓存。真实模型验收需要已授权的服务、可用凭据和费用预算；请勿把密钥、真实敏感日志粘贴到聊天中。配置真实服务并重启后端后再继续。
4. 选择已有事件，点击“查看证据”，对同一事件依次发起两次 AI 研判。首次成功且来源为 MODEL 后，第二次应显示 `CACHED`、引用首次研判 ID，新增输入与输出 token 均为 0。规则降级不缓存；两次之间不要更换模型、事件证据或等待超过 24 小时。
5. 回到安全概览，点击“刷新统计”：研判请求增加 2，缓存命中增加 1；模型尝试次数按实际尝试增加（若模型重试可能大于 1）；节省估算依据来源研判的已知 token 计算。逐次调用表显示模型、状态、耗时和已知 token。
6. 修改模型配置或更换证据后再次研判应显示 MISS。若模型服务未返回有效结果，应显示 RULE_FALLBACK，下一次继续尝试，不应误显示 CACHED。
