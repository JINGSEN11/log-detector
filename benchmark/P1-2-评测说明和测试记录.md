## 口径与限制

将每个“场景 × 规则”视为一个二元判定：场景内至少一条日志命中该规则即为预测正类；人工标签包括此场景期望的全部规则，未列出的 15 条规则视为负类。总共 31×15=465 个判定；行为窗口里的多条命中只算一次场景命中，不能与逐日志/事件统计直接比较。每个场景输入已视为脱敏后的结构化日志，不经过实际上传、解析或脱敏链路；R5、R6、R14 使用默认阈值及含边界窗口。分母为零的指标在报告中为 null。

仅规则与规则加研判的对比：测试先运行实际规则引擎，再对每个命中场景的证据构造一个模拟事件并调用真实 `EventAnalysisService` 的 Mock 模式；16 个命中场景均返回 `RULE_FALLBACK`、模型调用 0 次，15 个未命中场景不进入研判。这里每个场景模拟一个事件，**并非**生产事件聚合评测；Mock 是规则降级，不是模型预测。当前研判没有明确攻击/正常判决字段，其 confidence 也不是已定义的攻击概率，不能计算或声称规则加 AI 的分类 Precision/Recall/F1。真实模型对比需要另定事件级标注、判决口径、接入与费用授权。

## 手动复现

在项目根目录 PowerShell 中执行（路径必须是不存在的新文件；程序为保护已有报告拒绝覆盖）：

```powershell
mvn -f backend/pom.xml -Dtest=RuleEvaluationTest "-Devaluation.output=<项目根>/proceed/D5代码验收/P1-2-复验报告.json" test
```

1. 预期控制台显示 `scenarios=31`、`tp=17, fp=0, fn=0` 和 `BUILD SUCCESS`。
2. 用 VS Code 或其他文本编辑器打开新生成的 JSON：在 `micro` 查看指标，在 `perRule` 查看逐规则 TP/FP/FN，在 `details` 查看每个场景的 expected/actual/falsePositive/falseNegative，在 `dataset` 查看标注与输入。
3. 查看 `comparison`：命中场景 16、未命中场景 15、Mock 降级 16、模型调用 0；这说明规则与现有 Mock 研判的行为差异，不是模型效果对比。
4. 如果复验文件已存在，请换一个新文件名；无报告输出参数时，运行测试不会写报告文件。

本次不调用外部模型，不上传数据，也未改动产品业务逻辑。
